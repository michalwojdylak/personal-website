# LLM Inference Benchmarks: vLLM vs SGLang vs TensorRT-LLM on a Single L40S

Choosing an inference engine for large language model serving is a decision with direct impact on latency, throughput, and infrastructure cost. This post presents a **head-to-head benchmark** of three production-grade engines - **vLLM**, **SGLang**, and **TensorRT-LLM** - across four real-world workload scenarios on a single NVIDIA L40S GPU. I specifically chose the L40S because it is a practical, mid-range GPU that is less commonly featured in benchmarks - most published comparisons default to the H100, which may not reflect the hardware teams are actually deploying on. All benchmarks use Nvidia AIPerf for reproducible, standardized measurement.

> **Update (1 November 2026):** A technical reader pointed out that the engines were not compared on equal memory budgets, and that TTFT under heavy load is mostly time spent in a queue. Both points hold up against the raw data. TensorRT-LLM ran with an FP8 KV cache while vLLM and SGLang used the default BF16 one, so TensorRT-LLM kept about 2.4× as many requests generating at concurrency 64. Most of its throughput and TTFT lead at concurrency 32 and above, and in the long-context test, comes from that extra capacity rather than from faster kernels. The same applies to the FP8 vs 4-bit result in Experiment 3. The sections below have been corrected, and [Configuration Differences Between Engines](#configuration-differences-between-engines) lists everything that differed between the runs.

## TL;DR - Summary and Recommendations

![Engine comparison - normalized performance across key metrics](/images/blog/llm-inference-benchmarks/engine_summary.png)

### Engine Selection Guide

| Workload | Best Engine | Why |
|----------|-------------|-----|
| **Low concurrency, latency-critical** | vLLM | Lowest TTFT at c8 (834 ms); simple deployment |
| **High-throughput serving (c32+)** | TensorRT-LLM (as configured here) | 37% higher throughput at c64, from running 2.4× more requests at once on an FP8 KV cache; not yet tested against vLLM or SGLang with the same KV budget |
| **Long-context (8K+ tokens)** | TensorRT-LLM (as configured here) | 2× throughput, 7.5-8× faster TTFT; the TTFT gap is queueing, because vLLM and SGLang fit only 3 of 8 requests in their KV cache |
| **Streaming quality (smooth tokens)** | Not determined | SGLang's lower ITL at c32 and c64 comes from running fewer requests at once (about 20 vs 50 for TensorRT-LLM), not from faster decoding |
| **Highest measured throughput** | SGLang + MoE | 3.6× throughput using Qwen3-30B-A3B vs dense 32B |

### Key Takeaways

1. **TensorRT-LLM led at high concurrency and long context in this setup, mostly because it had more room for requests.** Its build script stores the KV cache in FP8, so it kept about 50 requests generating at concurrency 64, against about 20 for vLLM and SGLang with their default BF16 KV cache. Its higher ITL at high load is the cost of that larger batch. It also requires more complex deployment (engine compilation, model conversion).

2. **vLLM provides the best low-concurrency latency** and the most accessible deployment experience. The AWQ/GPTQ checkpoints it serves were 43% faster than the FP8 one, but that gain tracks KV cache capacity rather than the 4-bit kernels (see takeaway 5).

3. **SGLang's lower ITL at concurrency 32 and 64 is not evidence of faster decoding.** It was running about 20 requests at once against about 50 for TensorRT-LLM, and a smaller batch decodes each request faster. A fair ITL comparison needs equal batch sizes, which this setup did not have.

4. **MoE models are a game-changer.** The Qwen3-30B-A3B model running on SGLang outperforms every dense model configuration across all engines - by a wide margin on serving performance. These runs measure serving performance only, so evaluate output quality separately before treating the models as interchangeable.

5. **On vLLM, the 4-bit checkpoints won on memory, not kernels.** The tested AWQ and GPTQ checkpoints outperformed the tested FP8 checkpoint by 43% on throughput. Their smaller weights left vLLM 3.2× as much KV cache (82,448 tokens vs 25,584), so all 32 requests could run at once instead of about 20, and the throughput gain (1.43×) matches the larger batch (1.42×). Separating the kernels from the memory would need the same KV budget for every checkpoint, which has not been run yet. Measure output quality before making 4-bit the default.

## Test Environment and Methodology

All experiments run on a single machine with:

- **GPU:** NVIDIA L40S 48 GB
- **Model:** Qwen3-32B-FP8 (and variants for quantization/MoE tests)
- **Benchmark tool:** AIPerf v0.11.0
- **Protocol:** OpenAI-compatible `/v1/chat/completions` with streaming enabled
- **Warmup:** 30 requests excluded from results
- **Profiling:** 300 requests per run
- **Input:** Synthetic prompts with fixed token lengths (no variance)

### Required Software

- **CUDA Toolkit 13** - required by FlashInfer, which SGLang depends on
- **NVIDIA-SMI with CUDA 13** driver
- **`python3-dev`** - needed for building native extensions

### Key Metrics

| Metric | Description |
|--------|-------------|
| **Throughput (req/s)** | Completed requests per second across all concurrent users |
| **Output Token Throughput (tok/s)** | Total output tokens generated per second |
| **TTFT avg (ms)** | Time To First Token - end-to-end time from sending a request to the first streamed token, including queueing, scheduling and prefill. Prefill dominates for long inputs |
| **TTFT p99 (ms)** | 99th-percentile first-token latency: 99% of requests returned their first token at or below this value |
| **ITL avg (ms)** | Inter-Token Latency - average time between consecutive output tokens |

### Configuration Differences Between Engines

The engines were not configured identically, and some of these differences move the results more than the choice of engine does. Each item below is checked against the raw data in the repository:

- **KV cache precision and size.** `run_trtllm.py` quantizes TensorRT-LLM with an FP8 KV cache (`--kv_cache_dtype fp8`), which halves the memory per cached token. vLLM and SGLang were launched without a KV cache dtype setting, so they used their default (BF16 here). vLLM's own metrics show 1,599 KV blocks, or 25,584 tokens, for Qwen3-32B-FP8: room for 20 requests at their full 1,280 tokens. SGLang and TensorRT-LLM did not export server metrics, so their capacity is inferred from how many requests were generating at once (see [Experiment 1](#what-limits-each-engine-under-load)).
- **Output length.** TensorRT-LLM ran with `ignore_eos`, so every request generated exactly the requested number of tokens. vLLM and SGLang did not, but they generated the full length anyway: the mean output length was 256.0 tokens in every ISL 1024 run, and vLLM's server metrics show every one of those requests ending on the length limit, none on EOS. In the long-context runs the means were 510.6 (vLLM) and 509.7 (SGLang) out of 512, with 2-3% of requests stopping early. All three engines did the same amount of work to within 0.5%.
- **FP8 checkpoint.** vLLM and SGLang served Qwen's published `Qwen3-32B-FP8` checkpoint. TensorRT-LLM could not load it, so it served its own FP8 quantization of the BF16 `Qwen3-32B` (see [Workarounds](#tensorrt-llm-workarounds-applied)). The weights are not the same.
- **Long-context limits.** The ISL 8000 / OSL 512 runs need about 8,500 tokens per request, more than the run script defaults (`--max-model-len 8192` for vLLM, `--context-length 8192` for SGLang, `--max-seq-len 2048` for TensorRT-LLM). vLLM's metrics show it ran with a 9,216-token limit. The values used for SGLang and TensorRT-LLM were not recorded.
- **Server restarts.** The vLLM concurrency 8 run used a separate server launch with 1,918 KV blocks instead of 1,599. Only 29% of the cache was in use at concurrency 8, so this does not affect that result.
- **Request parameters.** The TensorRT-LLM concurrency 64 run also sent `min_tokens` and `max_completion_tokens` of 256, while its other runs sent only `ignore_eos`. TensorRT-LLM reports 1,032 input tokens instead of 1,024 because it was measured with `--use-server-token-count`, which counts the chat template too. The prompts are the same.
- **Prefix caching.** vLLM had prefix caching enabled but recorded no cache hits in any run, so cached prompts did not help it.

## Experiment 1: Concurrency Scaling

**Config:** Qwen3-32B-FP8, ISL = 1024, OSL = 256, Concurrency = 8 → 32 → 64

This experiment measures how each engine handles increasing concurrent request load - the most common production scaling scenario.

![Concurrency scaling - output token throughput](/images/blog/llm-inference-benchmarks/concurrency_throughput.png)

| Framework | Concurrency | Throughput (req/s) | Output (tok/s) | TTFT avg (ms) | TTFT p99 (ms) | ITL avg (ms) |
|-----------|:-----------:|:------------------:|:--------------:|:-------------:|:-------------:|:------------:|
| vLLM | 8 | 0.50 | 127.1 | 834 | 1,838 | 59.2 |
| vLLM | 32 | 0.95 | 243.9 | 11,125 | 25,768 | 84.7 |
| vLLM | 64 | 0.96 | 244.5 | 40,565 | 49,068 | 84.8 |
| SGLang | 8 | 0.45 | 115.7 | 2,029 | 2,609 | 60.6 |
| SGLang | 32 | 0.97 | 249.1 | 12,332 | 27,517 | 76.6 |
| SGLang | 64 | 0.98 | 250.1 | 40,601 | 53,767 | 77.8 |
| TensorRT-LLM | 8 | 0.46 | 117.9 | 2,541 | 2,891 | 54.0 |
| TensorRT-LLM | 32 | 1.13 | 289.2 | 4,554 | 10,325 | 83.0 |
| TensorRT-LLM | 64 | 1.34 | 342.1 | 11,738 | 42,304 | 124.4 |

![Concurrency scaling - TTFT](/images/blog/llm-inference-benchmarks/concurrency_ttft.png)

![Concurrency scaling - ITL](/images/blog/llm-inference-benchmarks/concurrency_itl.png)

### Analysis

**TensorRT-LLM dominates throughput at scale.** At concurrency 64, it delivers **342 tok/s** - **40% above** vLLM (245 tok/s) and **37% above** SGLang (250 tok/s). Its throughput continues to increase from c32 to c64, while both vLLM and SGLang plateau. The next section shows why: TensorRT-LLM was running about 2.4× as many requests at once.

**vLLM has the best low-concurrency latency.** At c8, vLLM achieves an average TTFT of just **834 ms** - 2.4× faster than SGLang (2,029 ms) and 3× faster than TensorRT-LLM (2,541 ms). This makes vLLM the best choice for low-traffic, latency-sensitive workloads. No engine was short of KV cache at c8, so this gap is not about capacity. vLLM's metrics show no queueing at c8 (0.01 s), with 0.60 s of prefill in its 0.83 s server-side TTFT. Why SGLang and TensorRT-LLM take longer at c8 was not measured.

**SGLang has the lowest ITL under load, but with a smaller batch.** At concurrency 32 and 64 it has the lowest inter-token latency (**76.6** and **77.8 ms**); at concurrency 8 TensorRT-LLM leads with **54.0 ms**, ahead of vLLM (59.2 ms) and SGLang (60.6 ms). At concurrency 64, SGLang was generating for about 20 requests at a time and TensorRT-LLM for about 50, so this is not a like-for-like comparison of decoding speed.

**TensorRT-LLM's TTFT stays lowest under load, because fewer of its requests wait.** At c32, TensorRT-LLM's TTFT is **4,554 ms** - less than half of vLLM's 11,125 ms and SGLang's 12,332 ms. At c64, the gap widens: TensorRT-LLM leads at **11,738 ms** vs ~40,500 ms for the other two. At these concurrency levels TTFT is mostly time spent waiting for a free slot, not prefill (see below).

**vLLM and SGLang gained almost nothing from c32 to c64.** Both show less than 1% extra throughput while TTFT more than triples. They were already at their KV cache limit at c32, so the extra 32 clients only lengthened the queue. More concurrency will not raise their throughput in this configuration; only a larger KV cache budget would. TensorRT-LLM still extracts meaningful throughput gain at c64 (+18% over c32), but at the cost of significantly higher ITL (124.4 ms).

### What Limits Each Engine Under Load

Once an engine's KV cache is full, new requests wait in a queue until a running request finishes. The table shows how many requests each engine was actually generating for at the same time. For vLLM this comes from its own Prometheus metrics. SGLang and TensorRT-LLM did not export server metrics, so for them it is counted from the per-request timestamps in AIPerf's `profile_export.jsonl`: requests between their first token and completion, averaged over the middle 70% of each run. For vLLM the two methods agree (21.0 from timestamps, 20.3 from the server, both peaking at 24).

| Concurrency | vLLM | SGLang | TensorRT-LLM |
|:-----------:|:----:|:------:|:------------:|
| 8 | 7.6 (max 8) | 7.1 (max 8) | 6.8 (max 8) |
| 32 | 21.0 (max 24) | 19.3 (max 24) | 27.0 (max 32) |
| 64 | 21.1 (max 24) | 19.7 (max 24) | 49.5 (max 53) |

vLLM and SGLang top out at 24 requests whether 32 or 64 clients are waiting. For vLLM that matches its 25,584-token KV cache: 20 requests at their full 1,280 tokens, a few more while some are still short. Its cache was 92% full on average at c32 and c64. SGLang's numbers match vLLM's, which suggests a similar budget. TensorRT-LLM's FP8 KV cache holds twice as many tokens per gigabyte, and it kept about 50 requests generating at c64. Each of its requests decodes more slowly (ITL 124.4 ms vs 84.8 ms for vLLM), but there are 2.4× as many of them, which is where its 40% throughput lead comes from.

vLLM's metrics also split TTFT into time spent waiting for a slot and time spent on prefill:

| vLLM, Qwen3-32B-FP8 | TTFT avg | Queue wait | Prefill |
|---------------------|:--------:|:----------:|:-------:|
| c8 | 0.83 s | 0.01 s | 0.60 s |
| c32 | 11.1 s | 9.4 s | 1.4 s |
| c64 | 40.6 s | 38.5 s | 1.4 s |

At c8, TTFT is prefill. At c64, 95% of it is queueing. The TTFT columns at c32 and c64 therefore measure batch capacity and scheduling, not attention kernel speed. A fair comparison of the engines under load needs the same KV cache budget on all three, which these runs did not have.

## Experiment 2: Long-Context Performance

**Config:** Qwen3-32B-FP8, ISL = 8000, OSL = 512, Concurrency = 8

Long-context workloads (document summarization, RAG with large context windows) stress the prefill pipeline disproportionately. This experiment uses an 8× larger input sequence to reveal engine-level differences in attention computation and memory management.

![Long context - throughput and TTFT comparison](/images/blog/llm-inference-benchmarks/long_context.png)

| Framework | Throughput (req/s) | Output (tok/s) | TTFT avg (ms) | TTFT p99 (ms) | ITL avg (ms) |
|-----------|:------------------:|:--------------:|:-------------:|:-------------:|:------------:|
| vLLM | 0.08 | 41.0 | 63,824 | 75,340 | 68.0 |
| SGLang | 0.08 | 38.2 | 68,593 | 82,825 | 72.6 |
| TensorRT-LLM | 0.15 | 75.9 | 8,560 | 38,053 | 88.4 |

### Analysis

**TensorRT-LLM won the long-context test in this setup.** It delivers **nearly 2× the throughput** (75.9 tok/s vs ~40 tok/s) and a **7.5× faster average TTFT than vLLM, 8× faster than SGLang**.

The TTFT gap is the most striking result in this entire benchmark suite: TensorRT-LLM returns the first output token in **8.6 seconds** on average, while vLLM needs **63.8 seconds** and SGLang needs **68.6 seconds**. It is not a prefill gap. Each request needs about 8,500 tokens of KV cache, and vLLM's 25,584-token cache fits three of them, so with eight clients five are always waiting. vLLM's metrics show 61.0 s of its 63.8 s TTFT was queue wait and only 2.5 s was prefill. SGLang never had more than three requests generating either. TensorRT-LLM, with its FP8 KV cache, kept up to seven generating (6.7 on average), so most of its requests started straight away and its median TTFT was 3.6 s. Token counts were equivalent and vLLM recorded no prefix-cache hits (see [Configuration Differences Between Engines](#configuration-differences-between-engines)), so neither explains the gap. These are still single runs.

**vLLM has a slight edge over SGLang** in both throughput (41.0 vs 38.2 tok/s) and TTFT (63.8s vs 68.6s), though both are significantly slower than TensorRT-LLM.

**TensorRT-LLM's higher ITL comes with a larger batch.** Its ITL of 88.4 ms is higher than vLLM (68.0 ms) and SGLang (72.6 ms), but it was generating for more than twice as many requests at a time (6.7 vs 2.8 on average). The data does not show TensorRT-LLM processing the input faster; it shows it admitting more requests at once.

## Experiment 3: Quantization Comparison

**Config:** vLLM, Concurrency = 32, ISL = 1024, OSL = 256

This experiment holds the inference engine constant (vLLM) and varies only the model checkpoint: FP8 vs AWQ vs GPTQ. Changing the checkpoint also changes how much memory is left for the KV cache, so it does not isolate the quantization format (see below).

![Quantization comparison - throughput and TTFT](/images/blog/llm-inference-benchmarks/quantization.png)

| Model | Throughput (req/s) | Output (tok/s) | TTFT avg (ms) | TTFT p99 (ms) | ITL avg (ms) |
|-------|:------------------:|:--------------:|:-------------:|:-------------:|:------------:|
| Qwen3-32B-FP8 | 0.95 | 243.9 | 11,125 | 25,768 | 84.7 |
| Qwen3-32B-AWQ | 1.36 | 349.3 | 2,770 | 11,617 | 78.9 |
| Qwen3-32B-GPTQ | 1.36 | 347.8 | 2,732 | 11,522 | 79.3 |

### Analysis

**The tested AWQ and GPTQ checkpoints dramatically outperform the tested FP8 one on vLLM.** Both 4-bit checkpoints deliver **43% higher throughput** (349 vs 244 tok/s) and **4× faster TTFT** (2.7s vs 11.1s) than FP8. This compares three specific checkpoints on one vLLM setup, not bit width in isolation: kernels, checkpoint configuration and implementation maturity all differ between the formats, and output quality was not measured here.

**AWQ and GPTQ are virtually identical in performance.** Throughput differs by less than 0.5%, and latency metrics are within noise margins. Both have almost the same KV cache budget and both fit the whole batch, so this says little about their kernels.

**FP8's worse performance on vLLM is explained by memory.** FP8 preserves more model precision (8-bit vs 4-bit), but its weights take roughly twice the memory, and vLLM's metrics show what that leaves for the KV cache:

| Checkpoint | KV cache tokens | Requests generating, avg (max) | KV cache used, avg | Queue wait | Prefill |
|------------|:---------------:|:------------------------------:|:------------------:|:----------:|:-------:|
| Qwen3-32B-FP8 | 25,584 | 20.3 (24) | 92% | 9.4 s | 1.4 s |
| Qwen3-32B-AWQ | 82,448 | 28.8 (32) | 40% | 0.8 s | 1.7 s |
| Qwen3-32B-GPTQ | 82,816 | 28.8 (32) | 40% | 0.8 s | 1.7 s |

At 1,280 tokens per request, FP8 has room for about 20 requests, so at concurrency 32 about ten are always queued, while the 4-bit checkpoints fit all 32. The throughput gain (349.3 / 243.9 = 1.43×) matches the larger running batch (28.8 / 20.3 = 1.42×), and FP8's average prefill was actually shorter (1.4 s vs 1.7 s). These runs do not show the 4-bit kernels being faster. Running FP8 and AWQ with the same number of KV blocks (vLLM's `--num-gpu-blocks-override`) would separate the kernel difference from the memory difference; that run has not been done yet.

**TTFT p99 gap is particularly significant.** FP8's worst-case first-token latency is **25.8s** versus **~11.5s** for AWQ/GPTQ - a 2.2× difference that directly impacts tail latency SLOs. Like the average, it is mostly queue wait.

## Experiment 4: MoE Model - Qwen3-30B-A3B

**Config:** SGLang, Concurrency = 32, ISL = 1024, OSL = 256

Mixture-of-Experts (MoE) models activate only a subset of parameters per token, promising higher throughput with lower compute. This experiment compares the dense Qwen3-32B-FP8 against the MoE Qwen3-30B-A3B-FP8, both served by SGLang.

![MoE vs Dense - throughput, TTFT, and ITL](/images/blog/llm-inference-benchmarks/moe_comparison.png)

| Model | Throughput (req/s) | Output (tok/s) | TTFT avg (ms) | TTFT p99 (ms) | ITL avg (ms) |
|-------|:------------------:|:--------------:|:-------------:|:-------------:|:------------:|
| Qwen3-32B-FP8 (Dense) | 0.97 | 249.1 | 12,332 | 27,517 | 76.6 |
| Qwen3-30B-A3B-FP8 (MoE) | 3.51 | 897.4 | 779 | 1,303 | 31.1 |

### Analysis

**The MoE model delivers a transformative performance advantage.** Qwen3-30B-A3B activates only 3B parameters per token out of its total 30B, resulting in:

- **3.6× higher request throughput** (3.51 vs 0.97 req/s)
- **3.6× higher token throughput** (897 vs 249 tok/s)
- **15.8× faster average TTFT** (779 ms vs 12,332 ms)
- **2.5× lower inter-token latency** (31.1 ms vs 76.6 ms)

Part of the difference is memory as well: the MoE run kept almost all 32 requests generating (28.9 on average), against about 19 for the dense model. Its 3.6× throughput combines a roughly 1.5× larger batch with 2.5× lower ITL per request.

These are the largest performance differences observed across all experiments. The MoE architecture fundamentally changes the compute profile - with only 3B active parameters, the model effectively runs like a much smaller dense model. This benchmark measures serving performance only, not answer quality, so a separate evaluation is needed before treating the two models as interchangeable.

**Sub-second TTFT at c32 is a standout result.** The MoE model achieves **779 ms average TTFT** even at concurrency 32 - faster than the dense model manages at concurrency 8 with any engine. Combined with a p99 TTFT of just 1,303 ms, this makes the MoE model viable for real-time, latency-sensitive applications at high concurrency.

## Limitations

These numbers come from one machine and one benchmark harness, and they are a starting point for choosing an inference stack rather than a universal ranking of engines:

- Each configuration was measured once. Run-to-run variability is not reported, so small differences should not be read as meaningful.
- The engines did not have equal KV cache budgets (see [Configuration Differences Between Engines](#configuration-differences-between-engines)). Throughput and TTFT at concurrency 32 and above, and in the long-context test, depend on that budget, so they compare these configurations rather than the engines themselves.
- The post does not publish the exact engine versions or commits or model revisions. Serving configuration is only partly recorded: the run scripts give the defaults and vLLM's metrics give its KV cache size and prefix-cache state, but the long-context limits and the KV cache sizes of SGLang and TensorRT-LLM were not saved. Results on another installation may differ for those reasons.
- No requests failed in any run. GPU utilization and memory consumption were not recorded.
- Output quality was never measured. Every comparison here is about serving performance.

Before making a production decision, benchmark your own model, prompt-length distribution, concurrency, latency SLOs, output quality and infrastructure cost.

## Reproducing These Benchmarks

All benchmark configurations, run scripts, and raw result JSON files are available in the [accompanying repository](https://github.com/michalwojdylak/llm-inference-benchmarks). Each framework has its own workspace directory with a `run_*.py` script and a `README.md` with step-by-step instructions.

```bash
# Example: Run SGLang benchmark with Qwen3-32B-FP8 at concurrency 32
cd sglang-workspace
python run_sglang.py --model Qwen/Qwen3-32B-FP8 --concurrency 32 \
    --isl 1024 --osl 256 --requests 300
```

The raw AIPerf JSON exports are stored in `aiperf-workspace/results/` and contain full statistical distributions (avg, p1-p99, min, max, std) for every metric - far more detail than the summary tables presented here.

### TensorRT-LLM: Workarounds Applied

Two issues required workarounds when benchmarking TensorRT-LLM:

1. **Token counting mismatch.** AIPerf was not counting tokens correctly when targeting TensorRT-LLM's OpenAI-compatible endpoint. The fix was to pass `--use-server-token-count` and `--ignore_eos` to the `aiperf profile` command, which delegates token counting to the server and prevents early termination on EOS tokens. These flags were used for TensorRT-LLM only. vLLM and SGLang generated the full output length without them; see [Configuration Differences Between Engines](#configuration-differences-between-engines).

2. **FP8 checkpoint incompatibility.** The pre-quantized `Qwen3-32B-FP8` checkpoint did not load correctly in TensorRT-LLM due to a configuration issue. To work around this, the `tensorrt-llm-workspace/run_trtllm.py` script was extended to first download the unquantized Qwen3-32B model and then quantize it to FP8 at build time. As a result, TensorRT-LLM served different FP8 weights from vLLM and SGLang, and the same quantization step also gave it an FP8 KV cache.

If you run into questions or issues while reproducing these benchmarks, please [open an issue on GitHub](https://github.com/michalwojdylak/llm-inference-benchmarks/issues).
